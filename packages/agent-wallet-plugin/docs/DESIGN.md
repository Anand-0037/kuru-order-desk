# Kuru Order Desk: approved prototype design

## Goal and boundary
An installable MetaMask Agent Wallet plugin that makes one user-confirmed Monad testnet MON/USDC limit-order lifecycle understandable: prepare a funding/risk summary, submit through the host wallet policy, reconcile receipt/fills/open remainder, and cancel the tracked remainder through the same policy. The product brief and scope were approved before this build; routine local engineering decisions are delegated. This prototype is not trading advice, unattended execution, a stop-loss, or a promise of profit/prize eligibility.

Only chain 10143 and the V2 market documented by Kuru are allowed. No mainnet switch, arbitrary contract/calldata input, direct private-key access, custom signing, hosted Relay, signer delegation, 7702, autonomous triggers, swaps, funding, or withdrawals. This build session runs offline fixtures and public read-only checks only. Live signing, wallet setup/funding, publication and submission remain human gates.

## Product and architecture
`mm kuru prepare --owner <address> --side buy|sell --price <decimal> --quantity <decimal>` obtains a single-block chain/account snapshot and creates an immutable local intent. All amounts are bigint internally and decimal strings in JSON. Reject extra precision, invalid tick/notional, missing registration, insufficient prefunded free balance, existing orders, wrong chain/deployment, stale snapshot, and custom post-fill hooks. Use GTC + POST_ONLY only. Summary states maximum reservation including maker fees, wallet gas availability (host estimates fees at authorization), no guaranteed fill, partial fills, and funds staying in AccountCore after cancel.

`mm kuru submit --intent <id> --confirm <digest> --exclusive-account` rechecks snapshot, selected wallet identity and order absence, expiry, parameters, funding and the intent digest before emitting one fixed-market batch via `ctx.walletExecutor`. Confirmation is a binding of exact reviewed data, not a substitute for MetaMask policy or the human financial-action boundary. No blanket yes flag bypasses host policy. One tracked active intent per owner/market. No transaction execution in fixture mode.

`mm kuru status --intent <id>` reconciles a successful receipt, relevant market logs and all 62 account slots at one block. It separates broadcast/receipt success from resting or filled quantities. Decode only the documented V2 receipt/log layouts, not incompatible hosted WebSocket streams. Packed bodies use our independent documented codec; envelopes still use the external SDK ABI. Log identity is block hash/transaction hash/log index/record index; data are ordered and deduplicated. Missing, conflicting, unfinalized or incomplete evidence is unknown/needs review rather than assumed filled/cancelled.

`mm kuru cancel --intent <id> --confirm <digest> --exclusive-account` refreshes status and verifies the stored order ID still occupies its tracked slot before one cancel-by-slot call. Filled/absent/reused slots are never blindly cancelled. Dedicated exclusive owner is a required operating assumption: preflight cannot eliminate a competing process's slot-reuse race between read and execution. The UI/docs must state that this direct path is unsuitable for concurrent trading. Cancellation cannot reverse fills. Reconcile resulting logs and slot at the same pinned block; absence alone does not prove cancellation.

## Persistence and retries
A per-state-directory atomic lock protects all mutations, with a guarded durable operation-phase record written before executor entry. Store an immutable intent plus submission/cancellation phases and resulting hashes. Flush atomic writes. A crash/timeout after entering submission without a hash is `submission-unknown`; never resend automatically. Known hashes can be reconciled after restart. Repeated/concurrent calls cannot initiate a second transaction. Lock recovery is explicit only after process liveness checks; ambiguous locks fail closed. Every persisted object is schema/version validated; path IDs are restricted. This is local crash resilience, not a protocol exactly-once guarantee.

## Acceptance and deliberate limitations
1. Offline tests cover prepare -> submit -> partial fill -> cancel, skipped post-only, filled-before-cancel, partial-fill/cancel race, stale/conflicting/incomplete logs, reordered/duplicate observations, wrong owner/chain/market, slot reuse, repeated calls, concurrent calls and restart recovery.
2. Typecheck, lint, generated oclif manifest and package contents pass. CLI fixtures work without any wallet or credentials.
3. Public read-only deployment/address/ABI facts are timestamped with sources; no live transaction claim is made from them.
4. Later human validation installs with explicit plugin consent, uses a dedicated prefunded testnet wallet, executes one approved real order/cancel lifecycle and records receipt/log/open-amount evidence. This gate is NOT satisfied by local tests.
5. README, architecture boundary, provenance, AI-use disclosure, honest demo script, setup/live validation and dependency-ordered checklist are present. No public repository/site or hackathon portal mutation occurs in this build.

## Review refinements: exact numerical and evidence contracts
`quantity` is sizePrecision units; raw MON = quantity × baseSizeMultiplier; exact parsing rejects fractional digits beyond the scale and never rounds. Both scales must be powers of ten. Price is positive uint32 and tick-aligned; quantity is positive uint96. The documented contract notional check is floor(floor(price × quantity / sizePrecision) × 10^quoteDecimals / pricePrecision). Show that value separately from a conservative funding estimate: ceil(price × quantity × 10^quoteDecimals / (sizePrecision × pricePrecision)); for a buy add ceil(estimate × effectiveMakerFeePps / 10^7). A sell requires quantity × baseSizeMultiplier MON atoms and maker fees reduce quote proceeds. These are snapshot funding estimates, not guaranteed execution-time cost caps. The direct batch ABI has neither a deadline nor a per-order maker-fee cap; a pending transaction may execute after local expiry or a fee/config change.

The immutable review fingerprint binds version, owner/root account, market/chain, side, price, quantity, scales, tick/notional bounds, effective maker fee, clientOrderId and expiry. Fresh balances/block/BBO may change without altering that fingerprint; a material fee or market-parameter change refuses submission and requires new preparation. Local intent expiry is five minutes. Snapshot age must be ≤30 seconds. Revalidate immediately before executor entry, while holding the local write lock.

For reconciliation, fetch market-wide logs, because a maker's fill is carried by another taker's event header. Bind maker records to account ID, order ID, side and physical slot; bind the original creation to submission hash, unique nonzero clientOrderId and operation index zero. Canonical fill identity is (chainId, orderBook, tradeId). Keep blockHash/transactionHash/logIndex/recordIndex as observation provenance and reject conflicting duplicate identities. Post-only creation supports RESTED or POST_ONLY_NOT_PLACED only; a taker-fill creation is an invariant error. Decode packed streams in canonical block/transaction/log/record order.

Read a finalized head, fetch a complete bounded range from original receipt block through that head, fetch the original receipt and current 62 slots at that block, then reread boundary hashes. Reject moving/orphaned boundaries, removed logs, receipt newer than head, decode errors, RPC range failures/truncation indicators, or a range above the local safety cap. Missing logs/slot disagreement yields `needs-review`; snapshot absence alone cannot prove a fill or cancel. Provider completeness remains an RPC trust assumption, exposed in the threat boundary. No hosted indexer assertion is promoted to chain truth.

A cancellation preview binds intent digest, tracked orderId/slot, current remaining quantity and expiry. Immediately before signing, fresh full reconciliation must still match the tracked order and reviewed remainder; a changed remainder asks for a fresh preview. The successful cancellation receipt must include the tracked order's non-sentinel deletion and quantity, followed by same-block slot reconciliation. A raced fill is retained, and only the remainder actually deleted is reported cancelled. Governance or unrelated deletion is distinguished from this plugin's own cancel. A reused slot is a hard refusal. Even with these checks direct slot cancellation is not concurrency-safe against another external writer; dedicated exclusive ownership is mandatory and explicitly disclosed.
